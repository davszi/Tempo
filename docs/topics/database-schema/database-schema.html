TEMPO Database Schema

TEMPO uses four SQLite tables for opening families, opening lines, practice history, and each player's repertoire and review schedule.

Opening lines are sourced from the Lichess chess-openings dataset.

Opening catalog structure explains why the opening tables have this shape: family sides, merged gambit families, the line tree and which lines can be learned.

opening_families 3 fields

FieldWhat it stores
family_idUnique family ID. Primary key.
nameUnique family name, such as Sicilian Defense. Accepted and Declined lines belong to their gambit's family, such as Queen's Gambit.
family_sideSide the family belongs to: white or black. Required.

opening_lines 6 fields

One row per opening line. Each line contains moves for both colors.

FieldWhat it stores
line_idUnique opening line ID. Primary key. Never reassigned.
family_idReference to opening_families.family_id. One family can have many lines. A line's side is its family's side.
parent_line_idReference to opening_lines.line_id: the longest other line of the same family whose moves start this line. Empty when there is none.
nameFull name of the opening line. Several lines can share a name.
ecoLichess opening classification code. Multiple lines can share a code.
moves_uciUnique ordered move sequence for White and Black in UCI notation. The line's permanent identity.

A line can be learned only when no other line names it as parent_line_id. This is derived, not stored. Learning a line that other lines extend is refused, and only learnable lines can join a repertoire. A line already in a player's repertoire stays reviewable if the catalog later gains a longer line.

Store.add_line takes moves in UCI; convert PGN first. It inserts a line or, when the moves already exist, updates that line's family, name and ECO code and keeps its line_id. A new family needs a side. The family side is separate from the side selected for a practice session.

When the backend opens an older database, it rebuilds the two opening tables in this layout inside one transaction, keeping every line ID and family ID and leaving practice history and progress untouched. The transaction rolls back if any reference would break or a family's side cannot be decided.

practice_events 12 fields

One row per suggestion, move attempt, or completed session.

FieldWhat it stores
event_idUnique event ID. Primary key.
player_idPlayer the event belongs to.
line_idReference to opening_lines.line_id.
session_idGroups events from the same session. Can be empty for a suggestion.
event_typeline_suggested, move_attempted, or session_completed.
modelearning or repeating.
sideSelected perspective for the session. Values are white, black, or both. Can be empty for a suggestion made before the player chooses.
occurred_atWhen the event happened.
move_indexPosition of the expected move in the full line. Filled for move attempts.
is_correctWhether the move attempt matched the expected move. Filled for move attempts.
response_time_msTime taken to attempt the move in milliseconds. Filled for move attempts.
fsrs_ratingAgain, Hard, Good, or Easy for a completed Repeating session.

player_lines 6 fields

One row per player and opening line. The primary key is (player_id, line_id).

FieldWhat it stores
player_idPlayer who owns this progress record.
line_idReference to opening_lines.line_id.
learned_atWhen the player first completed Learning for this line as White, Black, or Both.
last_reviewed_atWhen the player last completed a review of the line.
next_review_atWhen the line is due for review again.
fsrs_stateCurrent FSRS state used to update the review schedule.

Repertoire and reviews

  • A player's repertoire contains their player_lines rows with learned_at set. Later Learning sessions preserve the first completion date.
  • The planner opens a due line before the player selects White, Black, or Both. In Both, the player makes every move in one run. The full-line move_index identifies the color of each attempted move.
  • A completed review records one session completion in practice_events and updates last_reviewed_at, next_review_at, and fsrs_state once in player_lines.
